# 检索服务压力测试报告（服务端视角）

- 日期：2026-10-08
- 对象：全栈容器 `api / encoder / es01-03 / pg / mongo`
- 接口：`POST /api/v1/reports/search`
- 目标：找出容器崩溃的并发临界点
- **结论：未找到。并发加到 8192 仍未崩溃。**

---

## 1. 服务端配置

| 容器 | mem_limit | memswap | restart | CPU 限额 | 角色 |
| --- | --- | --- | --- | --- | --- |

| encoder | 4 GiB | 8 GiB | `no` | 无 | 单进程，合批窗口 5 ms |

| mongo | 512 MiB | 1 GiB | `no` | 无 | — |

- Docker VM：15.49 GiB RAM + 4 GiB swap（实测用量 7 MiB）
- 容器内存限额合计 **16.0 GiB > VM 15.49 GiB**
- 入口：`127.0.0.1:8000` 经 Docker Desktop 宿主机端口转发进容器（非直连）
- 监控：`stress/watch_containers.py`，每 2 s 采集 `docker stats` + `docker inspect` + `docker events`

### 2.1 8192并发时失败

8192 档的失败以**连接建立失败**为主，请求没到服务：

| 类型 | 次数 | 含义 |
| --- | --- | --- |
| `ConnectError: All connection attempts failed` | **42650** | 连接没建立 |
| 单请求 > 10 s | 8200 | 已连接，排队等响应等过头 |

连接路径与服务端计数器：

```
压测端 → [宿主机转发层] → [Docker 网络] → api:8000
             ①                 ②            ③
```

| 计数器 | 值 |
| --- | --- |
| `ListenOverflows` | 71 |
| `ListenDrops` | 71 |
| `TCPBacklogDrop` / `TCPReqQFullDrop` | 0 / 0 |
| `core.somaxconn` | 4096 |
| `ipv4.tcp_abort_on_overflow` | 0 |

**已排除**：服务端明确拒绝连接。
**未定位**：①②③ 中哪一段。`tcp_abort_on_overflow=0` 时内核静默丢弃 SYN，
`ListenOverflows` 未必增长，该计数器不足以定案。

## 5. 结论

1. 成功吞吐天花板 **119–197 req/s**；并发增 68 倍不变。瓶颈是 **CPU**（api 峰值 664%，es02 峰值 311%）。
2. **服务端没有崩，也没被压爆内存**：7 个容器全部档位 `OOMKilled=false`、`ExitCode=0`、`RestartCount=0`。
3. **8192 档 75% 的请求失败，失败在"连接建立"这一步**，请求没到服务。已排除服务端明确拒绝，具体位置未定位（§2.1）。
4. **"慢"与"连不上"是两步**：6144 档连接全部建立但 p50 达 47 s；8192 档才大面积连不上。
5. **api 内存首次成倍增长**：0.510 G → 峰值 1.043 G（占限额 34.8%），停止后不回落；其余六个容器不变。
6. **ES 负载不均**：es02 + es03 各约 200% CPU，es01 均值仅 44%。
7. 编码链路出现静默降级：HTTP 仍 200、`degraded` 不增长。
8. **未找到容器崩溃的并发临界点。** es02 空闲内存 81.5%，与并发无关。

---

## 6. 局限

1. 压测端与服务端共用一台 16 线程主机，绝对吞吐偏低；准确上限需第二台机器。但「并发增 68 倍而吞吐不变」的形态不受影响。
2. 6144 档以上 p95/p99 触顶客户端 60 s 超时；8192 档 p50 被秒失败的 `ConnectError` 拉低，均不代表真实延迟。
3. **连接失败的位置未定位**，只排除了服务端明确拒绝（§2.1）。
4. **api 内存峰值 1.043 G 是在"连接仍能建立"时测到的**，8192 档 74.9% 的请求未进入应用进程。
   **加大查询并发无法把内存推到限额**；内存是否会 OOM 未验证，需换攻击路径或换机器。
