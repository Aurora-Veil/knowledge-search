- 日期：2026-10-13
- 对象：全栈容器 `api / encoder / es01-03 / pg / mongo`
- 接口：`POST /api/v1/reports/search`
- 目的：用改动后的 api 镜像复现 `stress/report-p3.md` 的 4096 到 8192 三档，与该文档逐列对比
- **结论：三档均未劣化，成功吞吐高于原文档；8192 档的 75% 连接失败未复现。**

## 5. 新发现

改动后的 api 把 `search_log` 写入移到响应之后，高并发下偶发写不进去。

4096 与 6144 合并的那一轮，约 44000 次写入中出现 10 条：

```
search_log not recorded: PoolTimeout: couldn't get a connection after 2.00 sec
  File "/app/app/searchlog/store.py", line 71, in _write
    with get_pg().connection(timeout=_CONNECT_TIMEOUT) as conn:
```

8192 档负载更高，同样 0 条。

| 项 | 数值 |
| --- | --- |
| 每进程连接池上限 | `PG_POOL_MAX` = 10 |
| 四进程合计 | 40 |
| 等待连接的时限 | 2.00 s |
| 原文档各档丢弃 | 0 |

对吞吐无影响，比例约 0.02%，但对记录完整性是退步，需要单独处理。

## 6. 结论

1. **改动后的 api 在高并发三档均未劣化。** 成功吞吐 203.0 / 160.1 / 207.1 req/s，分别高于原文档同档 35.6% / 11.6% / 73.9%。
2. **原文档的 8192 档 75% 连接失败未复现。** 同样参数下连接建立失败 0 次，该失败不是 8192 并发的稳定特性。原文档 §2.1 与 §5 第 3 条据此可以划掉。
3. **成功吞吐的上限高于原文档所记。** 原文档结论 1 记为 119 到 197 req/s，本次三档落在 160 到 207 req/s，且 8192 档仍在 207 req/s，未见下降。
4. **服务端没有被压爆。** 七个容器三档全部 OOMKilled=false、ExitCode=0、RestartCount=0，api 内存峰值 1.105 G 占限额 36.8%。
5. **api 内存成倍增长后不回落的行为仍在。** 0.369 G 到 1.105 G 再到 1.035 G，与原文档 §5 第 5 条一致。
6. **ES 负载不均现象不稳定。** 原文档 es01 最低 44%，本次 es03 最低，两次的最高节点也不同。
7. **新增一条负面结论。** 后台写日志在高并发下偶发超时丢弃，见 §5。
8. **仍未找到容器崩溃的并发临界点。**

---

## 7. 局限

1. 只复现了三档，不是完整阶梯。原文档的 4096 档排在第 11 档，前面十档已经把索引预热；本次直接打 4096，条件是冷的，仍然更高。
2. 压测端与服务端共用同一台 16 线程主机。客户端核占用两轮不同，4096 档 0.95 对 1.62，6144 档 1.81 对 1.92。同机互抢使绝对吞吐偏低，也放大了两轮之间的差异。
3. 本次 8192 档实际并发为 7680。32 个分片中有 2 个在 `login()` 的 `/api/v1/auth/me` 上 `httpx.ReadTimeout` 而退出，未产出该档结果。即本次以少 6.25% 的客户端压力取得更高吞吐。
4. 6144 档与 8192 档的 p95、p99 顶在直方图上限 60000 ms，不构成延迟对比依据。
5. `watch_containers.py` 的事件流把历史事件一并写入，事件时间戳早于本轮压测开始时间，容器生死以 `docker inspect` 的采样列为准。
